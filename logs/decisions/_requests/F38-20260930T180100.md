# Decision Request: F38
**Type:** feature_start
**Feature:** Idle Sprites + Game Feel -- Activate unused idle/affection sprites with proper thresholds, add zzz particle for lie_down, and implement game feel systems (screen shake, hit-stop, floating coin popup, audio pitch randomization, camera lookahead, item_block bump animation).

**Pipeline:** plan-feature (Architect only, PLAN_ONLY mode)

## Decisions Pending

### D1: Screen shake implementation -- R3F hook vs camera manipulation
**Context:** Screen shake can be done by (A) directly jittering the camera position in CameraRig.tsx, (B) a dedicated `useScreenShake` hook that applies offset to the camera, or (C) a global shake store in Zustand. We need shake on block destroy and on damage.
**Recommendation:** Option B -- a lightweight `useScreenShake` hook that exposes a `shake(intensity, duration)` function and applies a decaying random offset to the camera each frame. The hook lives alongside CameraRig and reads a shared ref (or a tiny Zustand slice) so that GameScene3D can trigger shakes from callbacks. This keeps CameraRig clean and the shake logic testable.
**Risk:** Low -- camera offset is additive and does not interfere with deadzone logic.

### D2: Floating "+1" popup -- HTML overlay vs 3D text
**Context:** The coin popup could be (A) a 3D Text/Billboard in the R3F scene, or (B) an HTML overlay div positioned absolutely. Option A keeps everything in the 3D scene but requires a font/sprite. Option B is simpler and guarantees crisp text.
**Recommendation:** Option B -- HTML overlay. The HUD already uses absolute-positioned divs. A small `CoinPopup` component receives world coordinates, projects them to screen coordinates via the R3F camera, and renders a rising/fading "+1" span. This avoids adding 3D text geometry and meshes well with the existing HUD pattern.
**Risk:** Low -- screen projection is a standard pattern. If camera moves fast the popup may drift slightly, but the 0.6s lifetime makes this imperceptible.

### D3: Audio pitch randomization scope
**Context:** AudioManager3D.ts currently only handles background music tracks (maintheme, comeco). There is no SFX system at all -- no sound effects play in the game currently. Adding pitch randomization requires an SFX playback function first.
**Recommendation:** Add a `playSFX(name, opts?)` function to AudioManager3D.ts that plays one-shot HTMLAudioElements with configurable pitch via `playbackRate`. The pitch randomization (+-10%) applies automatically. This task should create the infrastructure but actual SFX audio files are out of scope (placeholder silent calls are fine). When real SFX files are added later (F40+), they will use this API.
**Risk:** Low -- `playbackRate` is well-supported across browsers. No new dependencies.

### D4: `affection` state trigger mechanism
**Context:** The `affection` animation should play when Mel collects a heart. Currently `healLife` is called directly from ChunkRenderer's `onHeartCollected` callback. We need to notify Mel.tsx that a heart was collected so the AnimationStateMachine can transition to `affection`. Options: (A) Add an `affection` boolean to AnimInput; (B) Pass a ref/callback from Mel.tsx up to GameScene3D; (C) Use a Zustand flag.
**Recommendation:** Option A -- add `heartCollected: boolean` to AnimInput. GameScene3D already passes `invincible` as a prop to Mel; similarly, add a `heartJustCollected` ref that is true for one frame after heart pickup. The AnimationStateMachine treats it as a one-shot state (0.6s) that auto-transitions back to idle. This keeps the pattern consistent with damage edge-detection.
**Risk:** Low -- follows exact same pattern as the existing `damaged`/`invincible` edge detection.

### D5: `wait` state vs `look_up` state
**Context:** The backlog says "use wait sprite when looking up for a while (>3s)." Currently, `look_up` plays immediately when holding up. The `wait` sprite is a distinct pose. We need to decide: does `wait` replace `look_up` after 3s, or is it a separate state?
**Recommendation:** Add a `wait` state to AnimState that triggers when `lookingUp` has been true for >3s continuously. The AnimationStateMachine tracks `lookUpTime` internally (or receives it via AnimInput). After 3s of lookingUp, transition from `look_up` to `wait`. When the player releases up, return to idle. This provides a natural progression: look_up -> wait (bored/impatient).
**Risk:** Low -- simple timer-based transition, same pattern as idle -> sit -> lie_down.

### D6: Item block bump animation approach
**Context:** When Mel hits an item_block from below, it should visually bump up and back. Currently item_block is a static RigidBody. Options: (A) Animate the mesh position inside Block.tsx via a ref; (B) Replace with a spring animation (react-spring); (C) Simple useFrame-based animation with a "bumping" state.
**Recommendation:** Option C -- add a `bumping` state to Block.tsx. When `activated` changes from false to true, set `bumping=true` and animate the mesh Y offset (up 0.15 over 60ms, back down over 120ms) via useFrame. No new dependencies. The RigidBody stays fixed; only the visual mesh moves.
**Risk:** Low -- purely visual, no physics interaction change.
