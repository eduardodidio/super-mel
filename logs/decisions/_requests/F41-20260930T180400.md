# Decision Request: F41
**Type:** feature_start
**Feature:** Progresso Salvo no Backend + Migracao Visitante para Conta -- Criar modelo Progress no Prisma (totalCoins + JSON flexivel para levelsCleared, stars, upgrades, bones, achievements). Backend GET/PUT /api/progress com auth JWT. Frontend sync: useGameState le progress do backend ao login e grava com debounce 2s. Guests continuam localStorage-only. Na criacao de conta (guest->registered), merge automatico: soma coins, uniao de levelsCleared.
**Requested at:** 2026-09-30T18:04:00Z
**Pipeline:** plan-feature (Architect only, PLAN_ONLY mode)

## Decisions Pending

### D1: Progress model cardinality (1:1 vs 1:N)
**Context:** Each player needs a progress record. Options: (A) 1:1 with @unique on playerId -- single row per player, partial updates via JSON merge. (B) 1:N with multiple progress snapshots -- more complex, allows history.
**Recommendation:** Option A -- 1:1 with @unique constraint. A single progress row per player keeps queries simple (findUnique by playerId), updates are PUT with deep merge on the `data` JSON field. No history needed at this stage; if needed later, an audit log table can be added.
**Risk:** Low. JSON merge is straightforward. If the data field grows too large (>1MB), we can split into dedicated tables. Current projected size: <10KB per player.

### D2: Auth middleware approach (preHandler vs per-route guard)
**Context:** Current routes (scores, levels) have NO auth middleware -- they accept raw playerId in the body. Progress routes need JWT verification since they expose/mutate player data. Options: (A) Fastify preHandler hook on the progress plugin. (B) Shared auth middleware extracted from JWT_SECRET.
**Recommendation:** Option A -- inline preHandler hook within progressRoutes that verifies the JWT from the Authorization header and attaches `request.playerId`. This keeps the change scoped to the new routes without refactoring existing unauthenticated routes. A shared middleware can be extracted later when scores/levels also need auth.
**Risk:** Low. Isolated change. Duplicate JWT verification logic is minimal (~10 lines) and can be DRY'd later.

### D3: Merge strategy on guest-to-registered conversion
**Context:** When a guest creates an account, their localStorage has totalCoins and possibly other progress. The new account has no backend progress. Options: (A) Frontend sends localStorage data to a dedicated POST /api/progress/merge endpoint. (B) Frontend calls PUT /api/progress after registration with the localStorage data. (C) Backend auto-creates empty Progress on register, frontend immediately PUTs localStorage.
**Recommendation:** Option C -- Backend creates an empty Progress row on /api/auth/register. After registration succeeds, the frontend reads localStorage, calls PUT /api/progress with the merged data. No special merge endpoint needed; the standard PUT with deep-merge handles it. This reuses existing routes and keeps the flow simple.
**Risk:** Low. Race condition is negligible (single user registering). If PUT fails, localStorage is still the source of truth and frontend retries on next mutation.

### D4: Debounce write strategy
**Context:** Every addCoin triggers a state change. Writing to backend on every coin would flood the API. Options: (A) Debounce 2s after last mutation. (B) Throttle every 5s. (C) Write only on game-over / scene change.
**Recommendation:** Option A -- debounce 2s. This ensures writes happen shortly after the player stops collecting coins (natural pauses in gameplay), while avoiding excessive API calls during rapid collection. A Zustand subscribe + setTimeout/clearTimeout pattern keeps implementation simple. Also trigger an immediate flush on scene changes (gameover, menu) to ensure no data loss.
**Risk:** Low. If the tab closes during the 2s window, at most 2s of progress is lost. Acceptable for a game.
