## Decisions Pending

### D1: Star calculation formula
**Context:** The result screen awards 1-3 stars per level. Need to decide what criteria map to each star tier.
**Recommendation:** 1 star = level completed, 2 stars = completed with zero deaths, 3 stars = zero deaths AND all coins collected. This is simpler than time-based thresholds (which require per-level target times that don't exist yet) and gives clear replay motivation. Time display is informational only for now; time-based stars can be added later when campaign levels (B-03) define target times.
**Risk:** Low -- star count is stored as a derived field on the client and can be recalculated.

### D2: Level mode death behavior vs infinite mode
**Context:** Currently `loseLife()` in useGameState transitions to "gameover" when lives reach 0. In level mode with checkpoints, the player should have infinite retries (deaths counter increments, respawn at last checkpoint). Game over should only apply to infinite mode (no checkpoints). This requires knowing whether the current play session is a "level" or "infinite".
**Recommendation:** Add a `gameMode: "infinite" | "level"` field to useGameState. In `loseLife()`, check gameMode: if "level", reset lives to 3 and increment deaths counter instead of transitioning to gameover. If "infinite", keep current behavior. The `resetGame()` sets gameMode to "infinite"; a new `startLevel(levelId)` sets gameMode to "level".
**Risk:** Medium -- loseLife is called from multiple places (Mel fall death, lava collision, invincibility callback). All paths already funnel through `loseLife()` so the change is centralized, but we must verify no path bypasses it.

### D3: Checkpoint data persistence during play
**Context:** Activated checkpoints and the "last checkpoint position" need to be tracked during a level session. Options: (A) Store in useGameState Zustand store, (B) Store in a ref inside GameScene3D, (C) Create a separate useLevelProgress store.
**Recommendation:** Option A -- add `lastCheckpoint: { x: number; y: number } | null` and `deaths: number` to useGameState. Keeps all game state in one store. The GameScene3D already reads from useGameState for lives, score, etc. Checkpoint activation calls `setLastCheckpoint(x, y)` on the store. On death in level mode, Mel teleports to `lastCheckpoint` (or spawnPoint if none activated).
**Risk:** Low -- adds 2 fields to existing store, no structural change.

### D4: Goal collision trigger mechanism
**Context:** When Mel touches the goal entity, we need to freeze gameplay and show the result screen. Options: (A) Set scene to "levelclear" immediately in the collision callback, (B) Play the jump_on_owner animation first (e.g., 1.5s delay), then transition, (C) Set a "levelCompleting" flag that freezes physics, show the sprite, then transition after a delay.
**Recommendation:** Option C -- introduce a `levelCompleting: boolean` flag. On goal collision: set `levelCompleting = true`, freeze Mel input, display the jump_on_owner sprite at the goal position for 1.5s, then transition to `scene: "levelclear"`. This gives a satisfying visual beat without abruptly cutting the scene.
**Risk:** Low -- the flag only affects the level completion flow. If jump_on_owner sprite loading fails, fall back to immediate transition.

### D5: Score saving for level clears
**Context:** The backend `POST /api/scores` already accepts `{ playerId, distance, levelId? }`. For level completions, we want to save: coins collected, time, deaths, stars. The current Score model only has `distance: Float` and `levelId: String?`.
**Recommendation:** Reuse the existing Score model for now. Map `distance` to `coins` count for level scores (or keep as 0). The star count, time, and deaths are derived client-side on the result screen but not persisted to backend yet. A future migration (B-03 campaign) will add `stars`, `time`, `deaths` columns. For now, the POST just records that the level was cleared with a `levelId`. This avoids a DB migration in F42.
**Risk:** Low -- no schema change, the record proves "player X cleared level Y". Richer data comes later.
