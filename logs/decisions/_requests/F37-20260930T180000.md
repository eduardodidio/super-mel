# Decision Request: F37
**Type:** feature_start
**Feature:** LevelData v2 + Editor com Entidades -- Evoluir o formato LevelData para v2 com suporte a entidades genericas (coins, hearts, goal, checkpoint, signs, bones, enemies), tema embutido, e missoes futuras. Adicionar tabs de palette (Blocos, Itens, Especiais) no editor e placement/removal de entidades na cena 3D. Inclui funcao de migracao v1->v2, conversor unificado levelToSceneObjects, e validacao backend.
**Requested at:** 2026-09-30T18:00:00Z
**Pipeline:** plan-feature (Architect only, PLAN_ONLY mode)

## Decisions Pending

### D1: EntityData position type (integer vs float)
**Context:** EntityData.x/y could be integers (grid-aligned) or floats (sub-pixel positioning for future use). Blocks are already grid-aligned integers.
**Recommendation:** Use `number` type but document convention as integer grid-aligned. This keeps the type simple and allows future sub-grid positioning without a breaking change.
**Risk:** Low -- no runtime cost, just convention.

### D2: Spawn point migration (spawnPoint field vs entity)
**Context:** v1 LevelData has `spawnPoint: { x, y }`. In v2, spawn could be an entity of type "spawn" in the entities array, or kept as a top-level field. Keeping both would be redundant.
**Recommendation:** Migrate spawn to an entity of type "spawn" in the entities array. Remove top-level `spawnPoint` from v2 interface. The migration function converts the old `spawnPoint` field into an entity `{ type: "spawn", x, y }`. This unifies all positional objects into a single system.
**Risk:** Medium -- all code reading `spawnPoint` must switch to finding the spawn entity. Mitigated by `levelToSceneObjects` returning a structured result with `spawnPoint` extracted.

### D3: item_block content association
**Context:** item_block is a BlockType (placed in the grid). Its content (coin, heart, power-up) needs to be defined somewhere. Options: (A) An entity of type "item_block_content" at the same x,y; (B) A `props` field on the BlockCell; (C) Random content at runtime.
**Recommendation:** Option A -- entity of type "item_block_content" co-located at the same grid position. The entity's `props.content` field specifies what the block drops. This keeps BlockCell unchanged and leverages the new entity system. If no entity exists for a given item_block, default to "coin" (backward compat).
**Risk:** Low -- simple lookup by position.

### D4: Backend validation depth
**Context:** The backend stores `data: Json` as JSONB. We could validate just the shape (has version, grid, entities) or deep-validate every entity and block.
**Recommendation:** Structural validation only -- check version, grid dimensions, entities array shape, and EntityType enum membership. Do NOT deep-validate every block/entity position. Keep it fast.
**Risk:** Low -- invalid positions are a client-side concern (editor prevents them).
