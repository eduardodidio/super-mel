# Task F44-T03 -- Wire Mel.tsx + Projectile.tsx to Resolved Config

**Feature:** F44
**Wave:** 1
**Type:** frontend
**Depends on:** F44-T01 (GAME_CONFIG + resolveConfig), F44-T02 (useShopState for equipped upgrades)

## User Story

As a player, I want my purchased and equipped upgrades (extra heart, extended fly time, turbo speed, etc.) to actually change how Mel moves and how projectiles behave during gameplay.

## Objective

Refactor `Mel.tsx` and `Projectile.tsx` to read all gameplay constants from `useResolvedConfig()` instead of local hardcoded constants. Implement the `double_jump` and `gentle_fall` upgrade mechanics in `Mel.tsx`. Implement the `double_ball` upgrade in `ProjectileManager`.

## Dev Notes

### 1. Refactor `Mel.tsx`

**Remove** the following local constants (lines 10-21):
```typescript
// REMOVE these:
const MOVE_SPEED = 6;
const MOVE_ACCEL = 25;
const FRICTION = 12;
const JUMP_FORCE = 10;
const JUMP_HOLD_FORCE = 6;

```

**Replace** with resolved config. Since `useResolvedConfig()` is a React hook and can't be called inside `useGameFrame`, pass the resolved config as a prop or read it once per component mount with a ref:

```typescript
// Option A: Read from ref (avoids re-render on equip change during play)
const configRef = useRef(resolveConfig([]));
useEffect(() => {
  const unsub = useShopState.subscribe((s) => {
    const ids = s.equipped.filter((e): e is UpgradeId => e !== null);
    configRef.current = resolveConfig(ids);
  });
  // Initial load
  const ids = useShopState.getState().equipped.filter((e): e is UpgradeId => e !== null);
  configRef.current = resolveConfig(ids);
  return unsub;
}, []);
```

Then in the `useGameFrame` callback, use `configRef.current.moveSpeed`, `configRef.current.jumpForce`, etc. instead of the old constants.

### 2. Implement `double_jump` in Mel.tsx

When `configRef.current.doubleJump === true`:
- Track `doubleJumpUsed` ref (boolean). Reset to `false` when grounded.
- On jump press while airborne AND `!doubleJumpUsed.current`:
  - Apply `JUMP_FORCE` upward velocity
  - Set `doubleJumpUsed.current = true`
  - Set `jumping.current = true`

Insert this logic after the normal jump block but before the fly section.

### 3. Implement `gentle_fall` (fallGravityScale) in Mel.tsx

When `configRef.current.fallGravityScale < 1.0` and `vel.y < 0` (falling) and NOT grounded:
- After setting linvel, multiply the Y velocity decay by `fallGravityScale`
- Approach: after the jump/fly logic, if falling: `rb.setGravityScale(configRef.current.fallGravityScale, true)`, else `rb.setGravityScale(1.0, true)`

Caution: `setGravityScale` is a Rapier method on the rigid body. Check that it exists. Alternatively, apply a counteracting upward force: `rb.applyImpulse({ x: 0, y: (1 - fallGravityScale) * mass * gravity * delta, z: 0 }, true)`.

### 4. Integrate `maxHearts` with config

In `useGameState.ts`, the `maxHearts` calculation currently uses:
```typescript
const maxHearts = useAssistMode.getState().fiveHearts ? 5 : 3;
```

This should be updated to:
```typescript
const baseMax = resolveConfig(equipped).maxHearts; // 3 or 4 from upgrade
const maxHearts = useAssistMode.getState().fiveHearts ? 5 : baseMax;
```

Note: Assist Mode's `fiveHearts` always wins (5 > 4). The `extra_heart` upgrade gives 4 hearts as a baseline.

### 5. Refactor `Projectile.tsx`

**Remove** the local `SPEED = 15` constant.

Since `Projectile` is a standalone component without direct access to hooks in its render loop, pass `speed` as a prop:

interface ProjectileProps {

The `ProjectileManager` (parent) reads the resolved config and passes `speed` down.

### 6. Implement `double_ball` in ProjectileManager

When `resolvedConfig.projectileCount === 2`, on each attack frame:
- Spawn 2 projectiles: one at normal position, one slightly offset vertically (+0.4 units Y, or -0.4). Both travel in the same direction.
- Use a small spawn delay (0 is fine; visual offset is enough).

### Gotchas

- **Performance:** Do NOT call `resolveConfig()` every frame. Use a ref + subscription pattern (or read once per mount and update on shop change). The shop state only changes when the player equips/unequips, which happens in the menu -- never mid-game.
- **Assist Mode interaction:** `fiveHearts` (assist) should override `maxHearts` (upgrade) when active. Handle the priority: if assist gives 5 hearts, that wins over the upgrade's 4 hearts.
- **`unlimitedFlight` (assist) vs `maxFlyTime` (upgrade):** Both paths must work. The existing `unlimitedFlight` check in Mel.tsx (line 169-177) bypasses the `MAX_FLY_TIME` limit. When the upgrade extends it to 8s, `MAX_FLY_TIME` becomes `configRef.current.maxFlyTime` (8 instead of 5). `unlimitedFlight` still bypasses it entirely.
- **Stamina bar:** The `StaminaBar` in HUD3D uses a hardcoded `flyTimeRemaining / 5` for the ratio. This must read the resolved `maxFlyTime` to display correctly when the fly_boost upgrade is active. Pass `maxFlyTime` as a prop or read from config.
- **doubleJump:** Make sure it doesn't interfere with the fly mechanic. The double jump should only trigger if NOT already flying. Suggested guard: `!flying.current && !doubleJumpUsed.current`.
