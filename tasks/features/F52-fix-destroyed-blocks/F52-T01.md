# Task F52-T01 -- Fix ChunkRenderer Block Destruction Mechanism

**Feature:** F52
**Wave:** 0
**Type:** bugfix
**Depends on:** none
**Status:** done

## User Story

As a player, when I destroy a block with the Bola do Infinito or by digging, the block
should immediately disappear from the screen and stop blocking my movement, so that
gameplay feels responsive and correct.

## Objective

Fix the `ChunkRenderer` component so that destroyed blocks are reliably removed from
both rendering and physics. Replace the fragile `useRef` + `setRenderTick` pattern with
a mechanism that guarantees React re-renders and properly unmounts the `Block` + `RigidBody`
components.

## Dev Notes

### Root Cause

The current `destroyBlock` implementation in `ChunkRenderer.tsx`:
```typescript
destroyBlock(x, y, z) {
  const key = `${x},${y},${z}`;
  if (destroyedBlocks.current.has(key)) return false;
  destroyedBlocks.current.add(key);    // mutate ref synchronously
  setRenderTick(t => t + 1);           // schedule re-render
  onBlockDestroyed?.(x, y);
  return true;
},
```

The problem is that `destroyedBlocks` is a `useRef(new Set())` and `renderTick` is a
dummy state variable used solely to force re-renders. Under React 18 automatic batching,
if other state updates are happening simultaneously (e.g., `setChunks` from the `useFrame`
callback), the `setRenderTick` update may be batched and deferred, leading to the block
persisting longer than expected -- or in pathological cases, not being filtered out at all
if a concurrent `setChunks` causes the component to re-render with stale closures.

### Fix Strategy

Convert `destroyedBlocks` from a `useRef(new Set())` to a `useState(new Set())`. This
guarantees that any mutation triggers a proper React re-render. Since `Set` is mutable,
we must create a **new Set** on each update to trigger React's shallow equality check.

**Before:**
```typescript
const destroyedBlocks = useRef(new Set<string>());
// ...
destroyedBlocks.current.add(key);
setRenderTick(t => t + 1);
```

**After:**
```typescript
const [destroyedBlocks, setDestroyedBlocks] = useState<Set<string>>(() => new Set());
// ...
setDestroyedBlocks(prev => {
  const next = new Set(prev);
  next.add(key);
  return next;
});
```

### Changes Required

**File: `packages/frontend/src/game/systems/ChunkRenderer.tsx`**

1. **Replace `destroyedBlocks` ref with state:**
   - Change `const destroyedBlocks = useRef(new Set<string>());` to
     `const [destroyedBlocks, setDestroyedBlocks] = useState<Set<string>>(() => new Set());`

2. **Remove `renderTick` state** (no longer needed):
   - Delete `const [renderTick, setRenderTick] = useState(0);`
   - Delete `void renderTick;`

3. **Update `destroyBlock` in `useImperativeHandle`:**
   ```typescript
   destroyBlock(x, y, z) {
     const key = `${x},${y},${z}`;
     let destroyed = false;
     setDestroyedBlocks(prev => {
       if (prev.has(key)) return prev;
       const next = new Set(prev);
       next.add(key);
       destroyed = true;
       return next;
     });
     if (destroyed) onBlockDestroyed?.(x, y);
     return destroyed;
   },
   ```

   **Important caveat:** The `destroyed` variable above will NOT work correctly because
   `setDestroyedBlocks` is asynchronous -- the updater runs later. Instead, use a
   ref-based check for the guard and state for the re-render:

   ```typescript
   destroyBlock(x, y, z) {
     const key = `${x},${y},${z}`;
     if (destroyedKeysRef.current.has(key)) return false;
     destroyedKeysRef.current.add(key);
     setDestroyedBlocks(prev => {
       const next = new Set(prev);
       next.add(key);
       return next;
     });
     onBlockDestroyed?.(x, y);
     return true;
   },
   ```

   Add a companion ref `const destroyedKeysRef = useRef(new Set<string>());` solely for
   the synchronous deduplication guard. The state `destroyedBlocks` is what drives
   the render filter.

4. **Update `activateBlock` similarly:**
   Convert `activatedBlocks` from ref to state using the same pattern. Add a companion
   ref `activatedKeysRef` for the synchronous guard.

5. **Update `getBlockAt`:**
   Use `destroyedKeysRef.current.has(key)` for the synchronous lookup (same behavior as
   before, the ref is the synchronous truth).

6. **Update `isBlockActivated`:**
   Use `activatedKeysRef.current.has(key)` (same as before).

7. **Update the render JSX:**
   Change `.filter((b) => !destroyedBlocks.current.has(...))` to
   `.filter((b) => !destroyedBlocks.has(...))` (since it's now state, not a ref).

   Change `activatedBlocks.current.has(...)` to `activatedBlocks.has(...)` in the
   `activated` prop.

8. **Update `handleDestroy` callback:**
   Change `destroyedBlocks.current.add(key)` to use `destroyedKeysRef.current.add(key)`
   and `setDestroyedBlocks(...)`.

### Key Constraint

The `setDestroyedBlocks` and `setActivatedBlocks` state updates will cause React to
re-render the `ChunkRenderer` component. Since `chunks` is also state, both will be
consistent in the same render pass. This eliminates the race condition.

Performance: Creating a new `Set` on each destruction is O(n) where n is the number
of destroyed blocks. Since blocks are destroyed infrequently (a few per minute at most),
this is negligible.

## Testing

### Unit Tests
- Call `destroyBlock(x, y, z)` and verify the block is no longer rendered in the JSX output.
- Call `destroyBlock` twice with the same key and verify it returns `false` on the second call.
- Call `destroyBlock` and verify `getBlockAt` returns `null` for that position.

### Integration Tests
- Fire a projectile at a destructible block (wood, glass) and verify the block mesh and
  collider are removed from the scene within 1 frame.
- Dig a block and verify it is removed.
- Destroy a block at a chunk boundary and verify no stale collider remains.

### Manual Tests
- Play the game and shoot destructible blocks. Verify they vanish visually.
- Walk through where the block was. Verify Mel passes through (no invisible wall).
- Destroy multiple blocks rapidly. Verify all disappear correctly.
